Two processes run in production: PHP, and the renderer. The only decision that
really matters is **which one faces the internet**, and it is not a matter of
taste — the two arrangements have different failure modes under load.

## Build first

```bash
composer install --no-dev --optimize-autoloader
npm ci && npm run build
```

`npm run build` writes the bundles to `bootstrap/rsc/vite`, the browser assets
to `public/build/rsc-vite`, and freezes every page it can into
`bootstrap/rsc/vite/static`. It runs `php artisan rsc:action-manifest` first, so
PHP has to be installed and bootable on the build machine.

Both processes then need the same `RSC_HOST_CALL_SECRET`. A mismatch answers
every host call with 403, which reads as the application refusing its own data.

## The renderer in front

The arrangement to reach for. The renderer answers the domain, serves assets
and frozen pages off disk, renders what is left, and calls back into Laravel
only for data.

```text
Browser → renderer (:5173) ──┬─→ assets, frozen pages: straight off disk
                             └─→ POST /__rsc/host-call → PHP-FPM
```

A PHP worker is occupied for the length of a **host call** — a query, a policy
check — and not for the length of a render. Static and frozen pages never reach
PHP at all.

```nginx title="/etc/nginx/sites-available/app"
server {
    server_name example.com;

    # Everything goes to the renderer.
    location / {
        proxy_pass http://127.0.0.1:5173;
        proxy_http_version 1.1;
        # Streaming: a page with Suspense boundaries reveals them as they
        # resolve, and buffering here holds every one of them to the end.
        proxy_buffering off;
    }

    # Except the host-call endpoint, which is PHP's and must not be reachable
    # from outside at all.
    location /__rsc/host-call {
        allow 127.0.0.1;
        deny all;
        include fastcgi_params;
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
    }
}
```

## Laravel in front

Set `RSC_RENDERER_URL` and Laravel proxies anything it does not route. This is
what development does, and it is why an app in Herd works at its own domain
with nothing configured.

In production it has a cost that is easy to miss:

:::danger[It can deadlock]
A PHP worker is held for the **whole render**, and the renderer calls back into
that same application for its data. With `W` workers that caps you at `W - 1`
concurrent renders — and if every worker is busy proxying, the host calls those
renders are waiting on have nobody left to answer them. Both sides then wait for
each other until something times out.
:::

If you want it anyway — a single box, an existing nginx you would rather not
change — give the host calls their own PHP-FPM pool so a proxying worker can
never starve a data worker:

```ini title="/etc/php/8.3/fpm/pool.d/rsc.conf"
[rsc]
user = www-data
listen = /run/php/php8.3-fpm-rsc.sock
pm = dynamic
pm.max_children = 10
```

Then point `/__rsc/host-call` at that socket and everything else at the default
pool.

## Keeping the renderer alive

It is an ordinary long-lived process. Bun or Node both run it.

```ini title="/etc/supervisor/conf.d/rsc-renderer.conf"
[program:rsc-renderer]
command=bun run server.ts
directory=/var/www/app
user=www-data
autostart=true
autorestart=true
redirect_stderr=true
stdout_logfile=/var/log/rsc-renderer.log
environment=RSC_HOST_CALL_SECRET="%(ENV_RSC_HOST_CALL_SECRET)s",RSC_BACKEND="http://127.0.0.1"
```

```ini title="/etc/systemd/system/rsc-renderer.service"
[Unit]
Description=RSC renderer
After=network.target

[Service]
User=www-data
WorkingDirectory=/var/www/app
EnvironmentFile=/var/www/app/.env
ExecStart=/usr/local/bin/bun run server.ts
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

## Docker

Two processes, and they are genuinely two — the renderer needs no PHP at
runtime and PHP needs no JavaScript runtime. Separate containers are the honest
shape, with `RSC_BACKEND` naming the PHP service:

```yaml title="compose.yaml"
services:
  php:
    build: { context: ., dockerfile: Dockerfile.php }
    environment:
      RSC_HOST_CALL_SECRET: ${RSC_HOST_CALL_SECRET}

  renderer:
    build: { context: ., dockerfile: Dockerfile.renderer }
    ports: ['5173:5173']
    environment:
      RSC_HOST_CALL_SECRET: ${RSC_HOST_CALL_SECRET}
      RSC_BACKEND: http://php
      RSC_RENDERER_HOST: 0.0.0.0
```

`RSC_RENDERER_HOST` matters here. The renderer binds `127.0.0.1` by default,
which inside a container means nothing outside it can connect.

The renderer image needs the build output — `bootstrap/rsc/vite`, `public` —
and `node_modules`. It does not need `vendor/`.

## Deploying a new version

```bash
npm ci && npm run build
php artisan config:cache && php artisan route:cache
sudo supervisorctl restart rsc-renderer
sudo systemctl reload php-fpm
```

Set `RSC_BUILD_VERSION` to something that changes per deploy — a commit sha
does. The client compares it on every navigation and falls back to a full load
when it changes, which is what stops a browser holding a layout from the old
build against payloads from the new one. Behind a CDN this matters more, not
less: the shell a client is holding may already be older than the payloads it
is asking for.

## Health checks

The renderer is an HTTP server, so any route works — including a page that is
frozen, which proves it is serving without touching PHP. To prove the whole
path, hit a route whose page makes a host call: a 200 means the renderer is up,
the secret matches, and PHP is answering.

## Checklist

- `npm run build` before every deploy, with PHP available for the manifest step
- The same `RSC_HOST_CALL_SECRET` in both processes
- `/__rsc/host-call` unreachable from outside
- `proxy_buffering off`, or streaming silently stops streaming
- `RSC_BUILD_VERSION` changing per deploy
- `RSC_RENDERER_HOST=0.0.0.0` if the renderer is in a container
- A process manager on the renderer
