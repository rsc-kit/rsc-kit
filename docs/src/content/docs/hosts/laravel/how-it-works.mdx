Everything in [How it works](/reference/how-it-works) applies here. What is
particular to Laravel is that there are two processes, and which one is in
charge is the opposite of what it used to be: the **renderer** owns the
request — routing, rendering, prerendered pages, assets — and calls into PHP
for the things only PHP can answer.

```text
Browser → the renderer (Vite in development, server.ts in production)
  ↓ matches the route, renders the tree
  ↓ a server component calls rpc('Orders.recent')
  POST /__rsc/host-call → Laravel
    ↓ the visitor's cookie, so the session and auth() are theirs
    ↓ runs App\Rsc\Orders::recent()
  ← JSON
  ↓ the render resumes
← streamed to the browser
```

## One endpoint, one shape

There is no protocol to implement. A host call is a POST with a JSON body and
a JSON reply, which is the whole of it:

```json
{ "function": "Orders.recent", "args": [{ "limit": 10 }] }
```

```json
{ "result": [ … ] }
```

The secret travels in `X-Rsc-Host-Secret`, and the visitor's `Cookie` header is
forwarded unchanged — which is why `auth()->user()` inside a callable finds the
person the page is being rendered for.

A bad or missing secret is answered **403** before anything is dispatched, so
the function is never reached. Note that the table below also has a 403, and it
means something else entirely: this one is the *caller* being refused, that one
is the *visitor*.

This used to be a length-prefixed frame protocol over a Unix socket, which
meant a client to write in every language that wanted to be a backend. It is
ordinary HTTP now, and a socket is a thing HTTP can run over rather than a
thing you have to speak.

## A refusal is not a failure

The reply keeps the outcomes apart, so the renderer never reads a message to
work out what happened:

| | Status | Reply |
| --- | --- | --- |
| Validation failed | 422 | `validationErrors`, keyed by field |
| Not logged in | 401 | `unauthenticated` |
| Not allowed | 403 | `unauthorized` |
| A middleware aborted | its own | `refusalStatus` |
| A redirect | **200** | `redirect` |

A redirect answers 200 on purpose. An HTTP client follows a 3xx transparently,
so a real one here would send the host call itself to the destination and hand
back whatever it found as the function's result.

## Middleware, without declaring a route

The renderer owns the route table, but Laravel still decides whether a route
may render. A colocated `route.ts` names middleware in Laravel's own
vocabulary, the names travel with the request, and PHP runs them through the
real pipeline against the real request before anything at or below that route
renders.

It fails closed: anything that is not a literal `true` is a refusal, so a
middleware that aborts, redirects or simply errors keeps the page from
rendering rather than being read as silence.

## What that means at build time

The prerender probe replaces the host global with a promise that never settles,
so a component awaiting `rpc()` suspends by construction. A page that reaches
into PHP for its data is therefore always PPR or dynamic — never accidentally
frozen with yesterday's rows baked into it.

That is a stronger guarantee than a pure JavaScript app gets, where the only
signal is whether the render finished inside the budget. See
[Partial prerendering](/guides/ppr) for what the build does with each outcome.

## Versions and deploys

The build stamps a version, and the client compares it on every navigation. A
client holding a stale one does a full load — a layout retained from the old
build has no claim on being right for the new one.

## Running it

In development, `npm run dev` **is** the renderer: Vite serves it, writes a
hot file, and Laravel proxies to whatever url that file names.

In production the renderer is `server.ts`, a long-lived process.
[Deployment](/hosts/laravel/deployment) covers which of the two processes
should face the internet, and why that choice matters more than it looks.
