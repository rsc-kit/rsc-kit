Two processes. A renderer, which owns routing and rendering; and your Laravel
application, which owns the data, the session, and whether a route may render.
They speak HTTP.

One command sets both up.

## Requirements

- **PHP 8.3+** and **Laravel 13+**
- **Node 24+ or Bun** — either runs the renderer and the build
- **Vite 8** — the plugin needs it, and a Laravel application ships an older one
- **React 19**

## Install

```bash
composer require rsc-kit/laravel
php artisan rsc:install
```

`rsc:install` does the PHP half itself — publishes `config/rsc.php`, generates
`RSC_HOST_CALL_SECRET` into your `.env` — and runs `rsc-kit init` for the rest.
Nothing you already have is overwritten. Where a file exists, the exact edit is
printed for you to make instead.

What lands:

| File | |
|---|---|
| `config/rsc.php` | the settings, published |
| `.env` | `RSC_HOST_CALL_SECRET`, generated |
| `vite.rsc.config.ts` | the RSC build's own config |
| `resources/js/rsc/app/` | a root layout and a page |
| `server.ts` | the renderer, for production |
| `package.json` | `dev` and `build` extended, `start` added |

Then install the JavaScript dependencies:

```bash
npm install    # or bun install
```

:::caution[Vite 8]
Every Laravel application ships a Vite, and at the time of writing none of them
ship Vite 8. The installer reports the version it found rather than upgrading
it for you — a Vite major moves your own asset pipeline too. Upgrade it before
building, or the build fails on a plugin API that does not exist yet, in an
error naming neither Vite nor this package.
:::

## Why a second Vite config

A Laravel application already has a `vite.config.js` with `laravel-vite-plugin`
in it. The two cannot share one file: both set an input list, an output
directory and a hot file, and whichever plugin runs second wins.

So the RSC build gets `vite.rsc.config.ts`. But it does **not** get its own
commands: `npm run dev` still means what it meant before, and now also runs the
renderer.

```json title="package.json"
{
  "scripts": {
    "dev": "concurrently -k -n assets,rsc \"vite\" \"php artisan rsc:action-manifest && vite --config vite.rsc.config.ts\"",
    "build": "vite build && php artisan rsc:action-manifest && vite build --config vite.rsc.config.ts",
    "start": "bun run server.ts"
  }
}
```

Both pipelines, one command. Your asset pipeline keeps building your Blade
assets; the renderer runs beside it. Asking you to learn a second command for
the thing you already have a command for is how the one you know silently stops
being enough.

If you had customised `dev` or `build` yourself, the installer will not touch
them — it puts the RSC commands at `rsc:dev` and `rsc:build` instead, and tells
you it did.

`rsc:action-manifest` runs first on purpose. Your server actions are found by
reflecting through Composer's autoloader — the only thing that sees what a
class inherits from its parents and traits — so PHP writes the map out and the
plugin reads it. Part of the command rather than a step to remember: a stale
map names a method that has since been renamed, and nothing fails until the
browser calls it.

## Development

```bash
npm run dev
```

Then open your application at its own url — `my-app.test`, whatever you already
use. Nothing else to configure, and no second address to remember.

Vite **is** the renderer in development. It writes a hot file while it runs,
Laravel reads that file, and any request Laravel does not route is handed
through. Stop the dev server and the file goes with it.

### Not using Herd or Valet?

Anything that runs several PHP workers is fine — Herd, Valet, FPM, Octane.
**`php artisan serve` is not**, and this is the one arrangement it cannot host.

:::caution[Why, and what to do instead]
`artisan serve` is `php -S`: a single worker that cannot answer a second
request while it is blocked on the first. This needs two — one is held for the
whole page while Laravel proxies it to the renderer, and the renderer calls
back to that same server for the page's data, with nobody left to answer. The
host call times out after 30s.

The page still answers **200**, because a failed host call is reported inside
its Suspense boundary rather than by failing the request. So the only symptom
is that every page with data takes exactly thirty seconds and comes back
missing it, with nothing in either log naming the cause. The package refuses
that shape up front instead, naming the backend it would have called.

There is no setting that fixes it — it is what the server is. Two ways around:

- **Serve the application on something with workers.** Herd or Valet, and
  nothing else to do.
- **Open the renderer directly**, at `http://localhost:5173`. It is the same
  two processes — Vite *is* the renderer in development — you are just skipping
  the proxy hop, which is the thing that needed the second worker. The dev
  server hands any url it does not own to the backend, so `/login`, a Blade
  page, a webhook and `/storage` are all still there: one origin, both halves.

  One caveat, and it is the reason this is not the default. `Host` cannot be
  forwarded — a vhost server routes on it, and Herd would have no such site —
  so the backend generates absolute urls (`url()`, `route()`, redirects, form
  actions) against **its** origin rather than this one. `X-Forwarded-Host` and
  `X-Forwarded-Proto` are sent so it can get this right, but they only take
  effect if the app trusts the proxy:

  ```php title="bootstrap/app.php"
  ->withMiddleware(function (Middleware $middleware) {
      $middleware->trustProxies(at: '*');   // dev only
  })
  ```

  Without it, pages render and links work; a Laravel *redirect* walks the
  browser onto the backend origin. Set `devFallback: false` on `rscKit()` to
  turn the whole fall-through off.

:::

## Your first page

Routes are files. The installer wrote these two:

```tsx title="resources/js/rsc/app/layout.tsx"
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <head>
        <meta charSet="utf-8" />
        <meta name="viewport" content="width=device-width, initial-scale=1" />
      </head>
      <body>
        <main>{children}</main>
      </body>
    </html>
  );
}
```

There is no Blade shell. The root layout renders the whole document, and the
build injects the bootstrap script and the stylesheet links into it.

```tsx title="resources/js/rsc/app/page.tsx"
export default function Home() {
  return <h1>Hello</h1>;
}
```

`app/page.tsx` is `GET /`, wrapped by `app/layout.tsx`. See
[File-Based Routing](/guides/routing) for the whole convention.

## Production

```bash
npm run build
npm run start
```

The build writes the bundles to `bootstrap/rsc/vite`, the browser assets to
`public/build/rsc-vite`, and freezes every page it can. `server.ts` serves all
three and calls back into Laravel for the data.

Both processes read `RSC_HOST_CALL_SECRET`, and a mismatch answers every host
call with 403. See [Deployment](/hosts/laravel/deployment) for how to put the
two in front of a domain.
