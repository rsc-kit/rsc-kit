There used to be a page here for each runtime, and a server file generated to
match. There is no server file now: [Nitro](https://nitro.build) builds one
around the route tree, and choosing where an app runs is choosing a preset.

```ts title="vite.config.ts"
import { defineConfig } from 'vite';
import { nitro } from 'nitro/vite';
import react from '@vitejs/plugin-react';
import { rscKit } from '@rsc-kit/core/vite';

export default defineConfig({
  plugins: [
    nitro({ preset: 'bun', serveStatic: 'inline' }),
    rscKit({ nitro: true }),
    react(),
  ],
});
```

`bun create rsc-kit my-app` writes that for you. Changing where it deploys is
changing the one string.

## The presets

`rsc-kit` asks about three, because those are the ones it can check for you.
Nitro carries [many more](https://nitro.build/deploy) and they need nothing from
this package — a preset is a string, not an integration.

| `--host` | preset | what you get |
| --- | --- | --- |
| `bun` | `bun` | `.output/server/index.mjs`, and `bun run compile` for a single binary |
| `node` | `node` | `.output/server/index.mjs`, run with `node` |
| `worker` | `cloudflare_module` | a Worker, plus the `wrangler.json` and `_headers` Nitro generates |

Everything else — Vercel, Netlify, Azure, Deno, AWS Amplify — is the same
change:

```ts
nitro({ preset: 'vercel', serveStatic: 'inline' })
```

## Running it

```bash
npm run dev      # vite is the renderer; nothing is prebuilt
npm run build    # writes .output/
npm run start    # runs .output/server/index.mjs
```

A Worker has no `start`, because it is deployed rather than started:

```bash
npm run preview  # wrangler dev, on workerd
npm run deploy   # nitro deploy --prebuilt
```

## Compiling to a single binary

Bun only, and the whole application ends up inside one file — engine, route
tree, frozen pages and assets:

```bash
npm run build
npm run compile   # bun build --compile .output/server/index.mjs
./my-app
```

<Aside type="caution" title="serveStatic: 'inline' is what makes this work">
  Without it the binary compiles, starts, serves pages, and 404s every asset.
  Inside a compiled binary the static path resolves into Bun's virtual
  filesystem — where the files on disk are not — and the failure is
  `ENOENT: /$bunfs/public/assets/…` with the pages themselves looking fine.

  The generated config sets it. If you write your own, set it too.
</Aside>

## Why `nitro` is pinned

The generated `package.json` pins an exact version rather than a range:

```json
"nitro": "3.0.260903-beta"
```

Nitro's own `latest` tag is a dated prerelease, and it sorts **above** the plain
`3.0.0` on npm. So `^3.0.0` resolves to the older release, which builds without
complaint and then answers 404 to every route. TanStack Start pins a dated beta
for the same reason.

## Mounting the handler yourself

There is no template for embedding the renderer in an existing Hono, Elysia or
Express app, because Nitro owns the server. The capability is unchanged —
`createRscHandler` is still exported, and anything the route table does not
claim comes back `null`, so your own routes still win:

```ts
import { createRscHandler } from '@rsc-kit/core/host';
import * as engine from './build/dist/rsc/index.js';

const rsc = createRscHandler({ engine });

app.all('*', async (c) => (await rsc(c.req.raw)) ?? c.notFound());
```

Import the engine bundle with a **static** path. A bundler decides what to embed
by tracing static specifiers, so resolving it at runtime leaves the engine out
of the build entirely.

## Assets are Nitro's

The build writes browser assets to `.output/public`, and Nitro serves them from
its own root. There is no `assetsDir` or `assetsUrl` to set — `rscKit()` refuses
both alongside `nitro`, rather than reading them and ignoring them:

```
[rsc-kit] assetsDir and assetsUrl cannot be used with nitro: Nitro publishes the
assets itself and serves them from its own root, so a prefix here would be
emitted into the markup and answered by nobody — every asset 404s while every
page still renders.
```

That refusal exists because the alternative was the silent version: the markup
asks for the app's prefix, Nitro answers at its own, and the page arrives
unstyled and never hydrates with nothing logged anywhere.

**For Laravel this is a change.** Assets used to live in `public/build/rsc-vite`
and be served by Laravel. They now live in `.output/public` and are served by
the renderer, which Laravel reaches through its proxy like any other unrouted
request. If you want nginx or a CDN serving them instead, point it at
`.output/public` — that directory is the deployment.
